# LifeOS Auto Bookkeeping

Implement a reliable path from an explicitly supplied payment screenshot or statement to the user's ledger. First inspect the target app's existing data model, OCR pipeline, import behavior, permissions, and tests. A Skill is guidance for the coding agent; the host application must implement the actual tools, storage, and platform integration.

1. **Capture and extract.** Accept the app's supported image or file input, preserve the original only according to the user's preferences, and prefer on-device recognition when available. A shortcut that passes a screenshot runs when triggered; do not represent it as automatic detection of every payment or as binding an external payment account. Verify any account connection or synchronization independently before claiming it exists.
2. **Interpret conservatively.** Distinguish the final paid amount from discounts, balances, original prices and status-bar numbers. Extract currency, expense or income/refund direction, merchant, status, and actual transaction date where available; use exact minor units rather than floating-point arithmetic. Treat pending, failed, contradictory or ambiguous payment state or amount as unresolved. Do not invent a merchant, date, or category; label any permitted fallback date as such.
3. **Save according to authorization.** Respect the user's selected automatic-save or review workflow. Only auto-save if the host can determine the amount and completed state to its required confidence and the user authorized that path. Clearly report the save result or reason an item needs review; failure must not appear as success. Do not request a duplicate confirmation solely because amounts match when the user chose automatic entry. Handle reliable source identifiers and conflicting records separately; preserve refunds and distinct transactions.
4. **Make changes traceable.** Save source type and extracted metadata needed for auditing without storing sensitive image content unnecessarily. Use transactional writes and the app's existing edit/delete or recovery facilities; never claim undo is available if it is not implemented. Distinguish transaction dates from capture dates and explain missing or uncertain dates.
5. **Verify with synthetic data.** Cover varied payment success and bill layouts, currency glyph OCR errors, conflicting candidates, failed/pending/refund states, merchant and date extraction, duplicate IDs, equal amounts on separate transactions, and save failures. Check actual ledger rows and UI feedback, and describe the boundaries of offline, provider and device tests separately. Do not copy real receipts, credentials or personal logs into public fixtures.
